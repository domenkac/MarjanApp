# MarjanApp — final P0 audit v1.0

Audit date: 9 October 2026. Baseline and inspected HEAD: `b41d3a9863be9eaf718be53937ba6c5b25feb87d` — Add two-company monthly E2E tests.

## Basis and interpretation

The acceptance criteria below come individually from `docs/01_PRD_v1.2.md`, §12.1 “P0 — brez tega ni izdelka”. Relevant PRD sections clarify each finding. Source and integration were inspected; a matching test name alone is not evidence of implementation. Test citations use repository-relative `file::function` notation. Some cited tests establish only the implemented portion of a partial requirement.

Status definitions:

- **IMPLEMENTED:** the required behavior is implemented and supported by the cited source/tests within the approved v1 scope. This is not a blanket production certification.
- **PARTIAL:** useful implementation exists, but required behavior, integration, or coverage remains incomplete.
- **MISSING:** the required behavior is absent; related fields or helpers do not implement it.
- **NEEDS_REAL_WORLD_VERIFICATION:** implementation exists, but acceptance depends on actual target-platform, external-service, or user verification not established here.

“Blocks production” means it prevents unconditional acceptance of the PRD product or production handover. **BLOCKER** prioritizes financial correctness, duplicate-delivery risk, and initial-readiness/data-recovery safeguards. **IMPORTANT** denotes other unfinished required product behavior. **VERIFICATION ONLY** denotes external acceptance work, not a proposed code defect. Partial requirements remain open even where no immediate financial danger is demonstrated.

The user reports a **completed Windows restore drill**. This audit accepts that fact but does not invent its logs, checksums, or sign-off. Production macOS restore remains unverified. Automated offline restore is separate evidence.

`app/settings.py::FEATURE_ESLOG` is `False`. PRD §10 “Odločitev o obsegu izdaje V1/V2” explicitly disables eSLOG UI and normal v1 orchestration, while retaining technical renderer/XSD/snapshot requirements. XML generation, delivery, and archiving are not available in the operational v1 cycle. The older wording in §10.4 “Prioriteta” still says XML is generated and archived for every invoice. This documentary tension is recorded, not silently converted into a new business rule. The explicit v1 decision and the requested audit of actual availability govern the availability descriptions below; turning on eSLOG is not proposed as a v1 release fix.

## P0 blockers by criticality

### BLOCKER

1. **Recipient VAT eligibility:** valid tenant data can still receive a restricted regime. This affects financial correctness (missing eligibility rule).
2. **Indexation effective date and invoice adjustments:** immediate source-amount replacement is not period-aware; late proposals never become approved next-invoice adjustment lines. January batch confirmation/exclusions are absent.
3. **Unresolved renewal:** expiry-window warnings do not implement confirmed renewal/history; an overdue auto-renewing lease can disappear before review and silently stop billing.
4. **First production readiness:** no full-chain wizard/global completion; missing probe evidence or missing companies can coexist with an issuable subset. Sample confirmation can be recorded without successful actual rendering/view. SMTP test success is not a prerequisite to first sending.
5. **Process interruption during SMTP:** caught socket errors become UNKNOWN, but a killed process can leave SUBMISSION_STARTED indefinitely. Supported user resolution accepts UNKNOWN only. Duplicate sending is blocked, but safe operational recovery is incomplete.
6. **Audit coverage:** source amount corrections and selected state changes are audited; ordinary company, lease, item metadata, catalog and recipient edits are not fully audited with reasons.
7. **Backup completeness and restoration:** uploaded contract attachments have no model/reference inventory; installed schedule is absent; cloud synchronization and macOS handover restore are unverified. Offline extraction is not an operationally reattached production restore.

### IMPORTANT

1. Manual ST invoice workflow, integrated service presets/free entry and NP/ST interleaving acceptance.
2. Operational storno/credit workflow; tested domain services alone do not let the user perform corrections safely.
3. Existing VAT calculation mode is editable, contrary to the explicit table criterion.
4. Historical archive divergence visibility and a working Archive navigation destination.
5. Safe physical-delete UI over existing protective services.
6. Persistent field explanations, complete six-step success/error display, and tabular-number PDF rendering/visual verification.

These remain required PRD work. They are not optional refactors or a reclassification to P1. Items intentionally withheld by PRD §10 do not authorize enabling eSLOG without a separate release decision.

### VERIFICATION ONLY

1. All five actual issuer configurations, starting sequences, separate mailbox identities and owner summary aggregation.
2. macOS Keychain backend, real SMTP connection/acceptance and actual PDF/CSV attachments at recipient mailboxes; BCC and failure behavior.
3. iCloud/Dropbox synchronization and availability from the intended external locations. Local named test folders are insufficient.
4. Restore on the target macOS installation following the operational manual, with immutable live-data evidence and recovered-application checks.
5. Excel opening under the actual accountant's locale; target-Mac PDF/fonts/signatures and alignment.

### T1 — Enforce recipient eligibility for restricted VAT regimes

Scope: the regime-to-tenant eligibility rule in model/service validation, source assignment forms and pre-issuance validation; reuse a single domain rule. No registry integration or tax-rule expansion.

Acceptance: an eligible legal entity passes; an individual, nonregistered entity or entity without the required full deduction cannot save/use the restricted regime or issue a frozen invoice that contains invalid eligibility evidence. Standard parking VAT remains allowed as specified in PRD §6.3. Rejection names the offending tenant/item/regime; no number is consumed. Add focused assignment and monthly integration tests.

Decision boundary: **Odločitev ni opredeljena v projektni dokumentaciji.** The exact persistent technical representation of a regime requiring this status is not present in the inspected model/spec sections. Confirm/document that representation before a schema change; do not infer a universal restriction from `OBDAVCENO` or from every `zahteva_referenco` row. Business eligibility itself is already required by PRD §6.3. This audit makes no new model decision.

### T2 — Complete January indexation and late adjustment integration

Scope: period-aware confirmed values; January index-entry/proposal/batch selection/exclusions; approved/rejected adjustment proposals integrated as separately traceable invoice lines; audit. Reuse existing calculation/event structures where possible. No automatic external index download.

Acceptance: confirming in January records February effect without changing January's billed value. February and later eligible periods use the confirmed value. Threshold/downward/no-clause conditions follow the contract. Exclusions and rejections retain reasons. Late entry proposes the required affected periods, accepted adjustments appear exactly once on the next invoice, rejected adjustments do not; issued originals never change. The first affected cycle requires individual review. Tests cover January/February, missed input, proration and retry/idempotence according to PRD §6.8 and FSD §4 “Januarska indeksacija” / §4.2 “Poračun ob zamujenem vnosu”.

### T3 — Make automatic renewal an explicit persistent event

Scope: pending renewal state, user confirm/cancel, renewed dates/history and billing integration; keep overdue pending events visible.

Acceptance: reaching or passing a fixed-term auto-renewal end cannot silently remove the lease or continue without the required resolution. Confirmation persists the new period; cancellation respects termination/proration. A cycle first opened after the end still shows the unresolved event. Ordinary fixed-term and indefinite leases retain their existing rules. Verify PRD §6.10 and §7.2; no invented renewal-date policy.

### T4 — Complete first-run readiness and sample/SMTP evidence

Scope: a resumable full-chain wizard, initial-completion evidence, all-five company checks, configured initial numbering, three location probes, actual sample rendering/explicit review and connection testing before first sending. Reuse existing forms, probe functions and separate confirmation models.

Acceptance: a blank installation cannot issue with incomplete chain, fewer than the required five ready issuers, stale/missing confirmations, failed initial location probe, or failed required first connection test. Every company's reviewed sample uses the actual template and never consumes a number, sends email or enters the official archive. Restart resumes setup. After completed setup, transient iCloud outage retains nonblocking delivery and pending archive per PRD §11.2. Do not introduce an undocumented permanent Dropbox-outage block. Keep accountant role outside setup approval.

### T5 — Reconcile interrupted invoice submission on restart

Scope: durable unresolved submission recovery after process termination; expose the existing documented UNKNOWN decisions without automatic resend. Do not invent a Sent-folder integration requirement where the provider cannot support it.

Acceptance: terminate a separate process after durable submission-start evidence and before durable definitive result; restart exposes “Rezultat ni znan – potrebno preverjanje”. No automatic second send; explicit verified-sent/not-sent decision requires a reason and audit. Not-sent retry preserves number, fiscal content, recipient snapshot and bytes; verified-sent enables archive. Avoid misclassifying a concurrently active sender as abandoned. A process-level test must exercise the durable boundary, not just a caught exception.

### T6 — Complete change auditing

Scope: required audit records for supported financial/master/catalog/recipient edits and indexation confirmation, using domain services and transactional writes. No broad unrelated refactor.

Acceptance: each changed field records time, old/new value and required reason; unchanged values do not invent changes. Failed audit rolls back the business edit. Minimal physical-delete audit remains minimal and never preserves whole deleted business content. Test representative high-impact edit paths and inspect coverage of every supported mutation entry point.

### T7 — Contract attachments, snapshot schedule and usable recovery

Scope: PRD §6.12 “Priloge k pogodbi (naložene datoteke)” storage/reference workflow; backup/restore reference completeness; install/document target-Mac invocation schedule; operational recovery procedure for path reconciliation and safe activation.

Acceptance: permitted uploaded attachment types/sizes and access paths follow §6.12; every referenced attachment is captured, recovered, checksum-checked where specified and openable. Missing reference fails verification with actionable feedback. Dated snapshots before/after cycle and actual scheduled execution are demonstrated. Preserve old generations; select a retention policy only if explicitly confirmed because PRD §11.3 gives a proposal, not a final number. Restore to a new directory protects live locations and source ZIP, then the approved activation procedure proves recovered application readability, sequence continuity and no duplicate sends. Production activation is separately authorized; this audit performs none.

### T8 — Manual ST and correction user workflows

Scope: ST gross entry/review/issue with service selector/free entry and presets; shared PDF delivery for the required standalone recipient; correction UI using existing services and original references. No eSLOG exposure in v1.

Acceptance: gross equals net plus VAT to the cent; mandatory individual review; ST number uses issue-year sequence; NP batch identity/counter unaffected by interleaved ST issuance. Storno/credit consume the original's sequence, leave original intact and carry references/reasons through PDF/report/delivery/archive. Confirmed-failure retry reuses exact artifact and number. No direct SQL or fabricated lease is required for standalone service invoicing.

### T9 — Finish required settings, archive and UI behavior

Scope: lock editing of existing VAT calculation mode; safe delete confirmation/reasons over existing services; working Archive destination and historical integrity warnings; missing help text; full six-step state presentation; tabular numeric PDF style.

Acceptance: crafted edits cannot change calculation mode; permitted deletes need explicit confirmation and preserve minimal audit; refused deletes explain dependencies and offer archive. A missing/modified older archived file becomes visible during the supported archive-check workflow. All six steps retain precise status text and success/error markings. Each PRD §16.2 field has permanent help. Target fonts render decimal columns vertically aligned in invoice/control PDFs and batch view.

## Recommendation

**NO-GO for unconditional production release/handover.**

The baseline provides substantial tested NP monthly behavior, immutable fiscal/artifact snapshots, concurrency-tested allocation, safe confirmed-failure retries, internal UNKNOWN decisions, dual local-file archive verification, CSV/accountant task workflows and offline restore. The remaining blockers are concrete required behavior, not merely absent broad test coverage: recipient eligibility, effective-date indexation/adjustments, persistent renewal, first-run/five-company/render/connection gates, process-interruption recovery, comprehensive audit and attachment-complete scheduled recovery.

Real SMTP/Keychain/cloud/Excel/five-company/macOS acceptance is also outstanding. The completed Windows restore drill is not downgraded or discarded. Intentional eSLOG disabling does not itself reverse the v1 scope decision or justify a production XML claim.
